# Per-page cloud-background toggles in UI Preferences

## Goal
Add on/off toggles in **Settings → UI Preferences** for the cloud background, one per page surface. Persisted per-user via the existing `Appearance` localStorage model. The `CloudBackgroundLayer` reads these settings to decide which pages show clouds.

## Pattern to follow (already in the codebase)
The `ShowScrollbar` component is the exact template: `Appearance.getSettings()` + `Appearance.updateSettings()` + the reusable `Toggle` component. I'll mirror it.

---

## Work breakdown

### 1. Extend the `Appearance` model with cloud settings
**File:** `src/models/appearance.js`

Add 4 boolean keys to `defaultSettings` and the `@typedef`:
- `cloudsOnSettings` (default `true` — settings pages preview clouds by default)
- `cloudsOnHome` (default `false`)
- `cloudsOnLogin` (default `true`)
- `cloudsOnChat` (default `false`)

### 2. Create the `CloudBackgroundPreference` toggle component
**New file:** `src/pages/GeneralSettings/Settings/components/CloudBackgroundPreference/index.jsx`

Mirrors `ShowScrollbar` exactly, but renders a labeled section ("Cloud Background") with **4 `Toggle`s** — one per surface (Settings pages, Home dashboard, Login screen, Chat workspace). Each toggle reads/writes its corresponding `Appearance` key. On change, dispatches a `clouds-updated` window event so the live `CloudBackgroundLayer` re-evaluates without needing a reload.

i18n keys added to `src/locales/en/common.js` under `customization.items.cloud-background` (title, description, and per-surface labels).

### 3. Mount the new component in UI Preferences
**File:** `src/pages/GeneralSettings/Settings/Interface/index.jsx`

Add `<CloudBackgroundPreference />` below `<ThemePreference />` (and above `<LanguagePreference />`), so appearance settings group together: Theme → Cloud Background → Language.

### 4. Make `CloudBackgroundLayer` settings-driven (per-page)
**File:** `src/components/CloudBackground/CloudBackgroundLayer.jsx`

Replace the hard-coded `CLOUD_ROUTE_PATTERNS` array with logic that:
1. Resolves the current surface from `useLocation().pathname` (`home`, `settings`, `login`, `chat`).
2. Reads the matching boolean from `Appearance.get(key)` (e.g. `Appearance.get("cloudsOnHome")`).
3. Shows clouds iff the resolved setting is `true`.

Subscribe to a `clouds-updated` window event so toggles take effect instantly while navigating. Keeps the `body.clouds-active` toggle CSS behavior intact.

### 5. Defaults summary
| Surface | Default | Rationale |
|---|---|---|
| Settings pages | **on** | Settings previews the feature it controls |
| Login | **on** | Strong first-impression branding |
| Home dashboard | off | Clean default; user opts in |
| Chat workspace | off | Readability-first default |

A fresh user sees clouds on settings + login (where branding shines), clean on home + chat (where they work). Fully adjustable.

## Out of scope
- Backend persistence (per-user DB storage) — using the existing localStorage `Appearance` model, which matches every other UI pref here. Backend sync is a separate task.
- Cloud style/intensity controls (color, density) — toggles are on/off only for now.
